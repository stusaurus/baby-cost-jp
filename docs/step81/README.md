## 計算と境界

- 必要枚数 = 1日枚数 × 日数。
- 購入セット数 = ceil(必要枚数 / **販売総枚数**)。内包パック数では割らない。
- 支払額 = セット数 × 掲載販売価格。余り = セット数 × 販売総枚数 − 必要枚数。
- 費用相当額 = 掲載販売価格 × 必要枚数 / 販売総枚数。既存の丸め済み単価を再利用せず、最後に小数1桁へ四捨五入。
- 数量は既存parserの piece・正整数・confidence≥0.88・根拠ありの値のみ。価格や数量の欠損/不正、送料根拠不明では支払額を表示しない。
- fetch_itemsで実際に利用した楽天の送料込み絞込 `postageFlag=1` を `shipping_basis=rakuten_postage_filter` として保存。レスポンスの postageFlag は異なる意味（0=込み、1=別）なので、矛盾する返却はunknownにする。商品名の「送料無料」から推定しない。旧カタログをアプリ側で自動補完しない。
- 金額は**掲載条件での購入計算**。配送地域の追加送料、販売価格変更、在庫、購入数制限、クーポン、ポイントは未確定。注文確認画面の金額を保証しない。
- サイズ予定が未入力なら予測しない。入力時は購入枚数と「使用枚数×予定日数」を比較して注意を出す。必要期間そのものは勝手に短縮しない。

## 検証方法

`python -m unittest discover -s tests -v` → `npm ci --ignore-scripts` → `npm test`。

既存preflightに `scripts/check_purchase_planner.cjs` を追加。Ubuntu24.04 / Playwright1.56.1、ChromiumとWebKit × 320/390/1440pxで操作する。通常の本番デプロイは起動しない。

ブラウザ試験は公開済み10商品スナップショットから実rendererでローカルページを再構築し、旧公開HTMLと価格・数量・商品順・楽天URL・metadataを照合する。旧スナップショットの送料込みAPI絞込宣言をテスト時だけ商品へ引き継ぐ（新アプリのunknown補完ではない）。最新楽天APIで在庫や支払を確定するテストではない。価格履歴の全記録はsnapshotにないため、既存履歴UIはPython回帰テストで保護する。

1セット/複数セット/大量余剰、プリセット・手入力・日数変更、不正入力時の古い金額消去、数量欠損、丸め、サイズ予定、価格順/容量順/単価順、保存、3商品トレー、共有、別サイズ/タイプ遷移、楽天URLとoperator_testを確認。GA4・楽天への通信を遮断し、クリックイベントはローカルの記録のみで検証する。結果と前後画像・Lighthouseは同じCIの `shared-comparison-evidence/purchase-planner-evidence` に保存。

新イベント `purchase_planner_use` は操作種別のみ（daily_preset/days_preset/daily_input/days_input/size_plan）。家庭の使用枚数・日数・サイズ予定・金額は送らない。初期表示や不正入力では送らず、purchaseイベントは作らない。

## 公開後の観測

承認・マージ後に本番ビルドと価格/送料根拠、ページ反映、楽天リンクを確認。GSCは同一URL×通常検索語の確定7日/28日表示・クリック・CTR・平均順位、URL Inspectionの最終クロールを追跡する。site:検索を通常検索と分ける。GA4はoperator_testを除外した計算機利用ユーザー・操作→比較トレー→affiliate_clickを観測し、楽天クリックを購入成果と扱わない。テスト成功やLighthouseを検索実績と混同しない。
